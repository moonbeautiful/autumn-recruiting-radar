# 配置边界

本项目把数据分成三层。只有第一层允许普通用户通过自然语言修改。

## 1. 用户偏好

运行文件：`runtime/user-preferences.json`  
模板：`config/user-preferences.example.json`

| 字段 | 用户能否修改 | 说明 |
| --- | --- | --- |
| `graduation_years` | 是 | 毕业届次，如`2027` |
| `role_keywords` | 是 | 目标岗位关键词 |
| `cities` | 是 | 目标城市；空数组表示全国 |
| `employment_types` | 是 | `campus`、`internship`、`conversion` |
| `company_type` | 是 | 想找哪类公司：`互联网大厂`/`AI独角兽·大模型公司`/`垂类·行业公司`/`都要`；决定第 1 步公司队列，名单实时搜出、不写死 |
| `company_preferences` | 是 | 公司偏好，默认只加分 |
| `industry_preferences` | 是 | 行业偏好，默认只加分 |
| `schedule.enabled` | 是 | 是否启用每日执行 |
| `schedule.time` | 是 | 本地时间，格式`HH:MM` |
| `schedule.timezone` | 是 | 默认`Asia/Shanghai` |

首次使用时由 Agent 询问求职条件并填写，不要求用户手动编辑 JSON。`schedule` 只在用户主动要求固定时间运行时修改，不属于首次问答。

> **定点运行的落地方式**：`schedule.enabled/time` 只是记录用户意愿。真正“每天固定时间自动跑”要靠外部触发器：优先用宿主客户端自带定时能力；宿主没有时用 [scripts/schedule_task.py](../scripts/schedule_task.py) 注册操作系统原生定时任务（macOS launchd / Linux cron / Windows 计划任务，路径运行时解析、不绑定设备）。两条限制须如实告知：①系统定时只在电脑开机时触发、关机不补跑；②定时任务默认只重新处理已有输入（去重/变化/截止），本身不联网搜岗。**新岗发现由“会话开始即自动联网增量搜集”承担（见 SKILL.md 6.1），对所有用户零配置、零成本；因此 `collector.command` 默认留空且应保持留空，不要为让定时任务搜新岗而硬编分发。**

## 2. 项目配置

文件：`config/project.json`

普通用户不应修改。它定义项目如何工作：

- 输入、状态和日志路径；
- 来源等级与优先级；
- 匹配权重；
- 公司和行业偏好的加分方式；
- 跨来源去重主键；
- 参与变化检测的字段；
- 分阶段流式发现（`discovery`）：公司队列的来源顺序、第一批 / 单次公司数上限、每家条数上限、并发上限、以及雇主排序锚点；
- 截止时间与页面关闭的判定规则；
- 内部快照、聊天清单和状态保留规则；
- 后台搜集命令及输入新鲜度要求；

如果迁移到不同 Agent 宿主，只允许维护者修改 `collector.command` 和相关运行路径。

## 3. 运行状态

目录：`runtime/state/`

用户和 Agent 都不应直接修改：

- `seen.json`：跨次运行的稳定状态；
- `jobs.json`：本次仍有效的岗位；
- `expired.json`：已截止岗位；
- `rejected.json`：字段无效或不满足合同的记录；
- `daily/`：完整内部快照；
- `outbox/`：本次聊天清单的内部副本。

如果需要清空历史，应先备份整个 `runtime/state/`，再使用维护命令处理，不要手动删改单条状态。

## 设计原则

> 用户只描述想找什么；项目配置决定如何搜集、核验、匹配、去重和判断变化；运行状态由程序自动维护。

公司和行业偏好默认不做硬过滤，避免因为偏好描述过窄而漏掉岗位。届次、岗位、城市和招聘类型属于硬条件。

前台交互始终走当前聊天：搜集完成后直接回复岗位清单。不要再询问通知渠道，也不要默认启用系统通知。
